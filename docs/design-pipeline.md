## GET /api/health

Input: no body, credentials, or user data. Success HTTP 200: `{ "status": "ok", "database": "ready", "model_configured": false }`; model_configured is a boolean indicating only a nonblank backend key, never a live-provider check. A request-time database error returns HTTP 503 with `{ "detail": "Local database is unavailable." }` and no internal path or key. A startup database failure stops startup rather than claiming readiness. Repeated health checks use a read-only connection and do not alter records. CORS permits only the configured exact local development origins; no credential cookies are used.

The frontend reads /api/health through Vite’s local proxy, with a three-second timeout. It shows a small Backend ready/unavailable indicator and continues to support every screen either way. No keys or configured model names are returned to the browser. The additional Stage 2 activity endpoints are documented below.

Worked example: a fictional reviewer opens Pause and skips the popup; home is available immediately. A successful /api/health request reports database ready. If the backend is stopped, the indicator reports unavailable while exercise navigation, Exit, mood dismissal, and locally bundled crisis information still work.

After elapsed time reaches 60 seconds it transitions once to completion. No counters accumulate callback intervals. ### Activity API contracts (implemented)

All requests below require `X-App-ID` (UUID). Dates are device-local ISO calendar dates; timestamps are offset-aware and normalized to UTC. Successful requests return HTTP 200 with the full scoped record; writes never return secret configuration. Extra input fields are rejected. There is no bulk-history view or unauthenticated list of all sessions.

| Method/path | Validated input | Successful record / failure behavior |
| --- | --- | --- |
| POST /api/sessions | id UUID, exercise_type paced_breathing/stop, started_at timestamp, entry_duration_seconds nonnegative finite | Starts one row. Same identical start returns existing row even after completion; same ID/different payload or owner is 409. |
| PATCH /api/sessions/{id} | status completed/exited, ended_at timestamp, duration_seconds nonnegative finite | Updates that started row. Identical terminal retry returns unchanged record, conflicting terminal update is 409. End cannot precede start; timestamp duration must agree within 1 second; breathing completion needs ≥60 seconds. |
| PUT /api/sessions/{id}/feedback | feedback helpful/not_helpful/skipped | Completed sessions only (otherwise 409); updates feedback without changing timestamps/status. Deliberate new choices replace feedback, duplicate choices are idempotent. |
| GET /api/sessions/{id} | scoped ID and header | Returns row; unknown/wrong identity is 404. No model call. |
| PUT /api/mood-checkins/{local_date} | mood calm/okay/anxious/overwhelmed/skipped | One row per app/date. Same retry returns original creation timestamp; conflicting choice is 409. |
| GET /api/mood-checkins/{local_date} | scoped date/header | Returns daily row or 404. |

Schema: exercise_sessions has id PK, app_id, exercise_type, started_at, ended_at nullable, status started/completed/exited, duration_seconds, entry_duration_seconds, planned_duration_seconds=60, and nullable feedback. Constraints disallow feedback on unfinished/exited rows and end timestamps on started rows. daily_mood_checkins has composite PK(app_id, local_date), mood/skipped enum, and server-generated created_at. app_metadata schema_version is 2. Initialization uses CREATE IF NOT EXISTS and a transaction, never reseeds exercises, and rejects unsupported newer schema versions. SQL uses bound values and no model involvement; concurrent writes use BEGIN IMMEDIATE so the first terminal update wins.

Duration is measured from the first mounted instruction to the final planned phase/Finish/Exit using the monotonic clock, rounded to milliseconds. Entry/setup (card selection to first instruction) is stored separately; no backend wait is included in entry. ended_at is anchored to the start UTC timestamp plus measured monotonic duration, so changing the system clock during an exercise does not make end precede start. STOP actual time includes voluntary reflection/backtracking/background time, whereas the 60-second intended path excludes extra user pauses. Opening support ends timing first, so time reading support is excluded. Browser/OS suspension precision can vary; breathing exits when the document becomes hidden, consistent with the established safety rule, instead of silently completing unseen cycles. Interruptions use exited status in the Stage 2 schema, not a new interrupted enum.

A per-session recorder starts a request after the instruction mounts. Exit/complete synchronously freezes one terminal snapshot and changes screen, then the queued save waits for start acknowledgment. If a start/terminal acknowledgment failed, a later feedback choice can replay that same ID/start/terminal idempotently before feedback. No unbounded or automatic retry loop exists. Queue revisions prevent an old acknowledgment from announcing success while a newer save is pending. A recorder updates only its own UI state, so stale earlier-session responses cannot change a newer session. Failure text explicitly says not saved; navigation/safety never awaits the queue. Returning home without feedback queues skipped; failed/unfinished sessions are not fabricated as completed.

Writes use a 3-second timeout with keepalive enabled. pagehide submits a best-effort exit, but a reload, browser termination, or offline failure before the queue drains can leave a started record or lose an unsaved mutation. There is no durable offline outbox or cross-reload retry yet, and the UI never claims these writes succeeded. Mood dismissal is immediate locally even when its write fails; no previous Part 3.1/Stage 1 mood value is invented/backfilled. Existing Stage 1 daily markers may suppress an already answered popup today without a new SQLite row. A record's mood is self-report only and never selects/reorders an exercise here.

Worked fictional example: the user starts STOP with session UUID S (a valid UUID, not literal S), manually finishes after 64.2 seconds, and selects Helpful. The database has exactly one completed stop row, duration_seconds=64.2, planned_duration_seconds=60, and feedback=helpful. Replaying the start or exact finish does not insert a second row or clear feedback. A competing exited update returns 409. If SQLite is unavailable, all these screens still navigate and the footer/completion says not saved.

Technical references for this increment: [monotonic performance timing](https://developer.mozilla.org/en-US/docs/Web/API/Performance/now), [FastAPI typed request bodies](https://fastapi.tiangolo.com/tutorial/body/), and [SQLite transactions/parameter binding](https://docs.python.org/3/library/sqlite3.html). These references explain implementation mechanisms, not clinical effects.

## Stage 3 contract — optional conversational feedback

The latest request authorizes a response directly after Helpful/Not Helpful; this replaces the earlier separate “Show a brief response” opt-in. Skip still makes no model request. Exercises, timing, crisis content, and navigation remain independent. No key or actual backend/.env is configured, so the default is an explicitly labeled deterministic mock, not a verified live language model. A provider-neutral async generate(context) boundary supports an optional backend-only chat-completions HTTP adapter patterned after the inspected Expedia Lite request/config separation. No provider is permitted to access SQLite or tools.

POST /api/feedback-response accepts a request UUID, completed session UUID, matching exercise type, Helpful/Not Helpful enum, and the exact predefined non-sensitive button message. Extra/arbitrary text is rejected. X-App-ID scopes the session. The controller first reserves one conversation/user message transactionally, then releases SQLite while making at most one provider call with a four-second deadline, validates the result against reviewed short neutral outputs, and saves only the actual accepted reply. The response reports succeeded/failed/pending, ordered messages, mock/live source, and an explicit UI fallback on failure. Fallback copy is never an assistant/model record. GET /api/conversations/{id} retrieves the scoped saved exchange. No history screen or RAG is added now.

There is at most one conversation per (session, feedback), each with one fixed user message and at most one accepted assistant reply. Repeated IDs/buttons reuse the persisted exchange without extra calls; pending duplicates get 202. Failed attempts retain the user message plus a safe failure code, never raw rejected content/errors/credentials. Pending exchanges interrupted by a backend restart are marked failed with no fabricated reply. Database failures report unsaved HTTP 503, preserving the already completed exercise. Output controls are application-owned, not prompt-only: exact reviewed neutral text, maximum length/two sentences, plain text rendering, no tools/action payloads, no model writes.

### Failure, safety, inspection, and limits

Missing credentials in live mode fail before network access. HTTP adapter requires an HTTPS endpoint without user info/query/fragment, rejects redirects/non-success/tool/function payloads, limits received body to 64 KiB, and uses finite connection/read and total deadlines. Unexpected errors map to safe codes. Mock mode never needs a key. No frontend/model-controlled instructions, navigation, timing, support links, tools, or writes are accepted. The reviewed output is rendered as text, without HTML or executable actions.

This endpoint accepts no free text. A fictional crisis-related string or extra mood/history field is rejected with 422 without a provider call; it is not classified, diagnosed, monitored, or saved as conversation text. The product cannot detect all distress, and fixed buttons cannot reveal intent. Independent bundled crisis access remains available; no generated support advice is needed. Existing resource content was preserved and its earlier verification is recorded separately.

Duplicate requests return the original persisted exchange, even when failed. At most two exchanges (one per non-Skip choice) can exist per session. A changed feedback choice changes the session's latest feedback but does not erase the earlier conversation context. No automatic retry/polling is implemented. Skip/Home abort client waiting and suppress stale display; an already submitted server call may finish and save. Pending rows on startup become failed/interrupted; this reconciliation assumes the single-process loopback server, not multiple workers. A final DB failure can leave pending until restart; no fabricated assistant is returned. Database-offline failures cannot themselves be durably recorded, and the UI says not saved. Health is checked once per load and can be stale after stopping services; per-operation save/fallback states remain authoritative.

Inspect data/app.sqlite3 with DB Browser for SQLite if already available (not installed or operated in this stage), or Python sqlite3 read-only mode. Repeatable query:

```sql
SELECT c.id, c.session_id, c.feedback, c.provider_mode, c.status, c.failure_code,
       m.id AS message_id, m.ordinal, m.role, m.content, m.created_at
FROM conversations c LEFT JOIN messages m ON m.conversation_id=c.id
WHERE c.app_id=:app_id ORDER BY c.created_at,c.id,m.ordinal;
```

### Implemented recommendation/context API and schema 5
